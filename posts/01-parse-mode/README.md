# 01. Разметка в Telegram: почему «отправилось» ≠ «понялось»

## Что случилось

Пост с заголовками, кодом и таблицей ушёл в канал обычным текстом: вместо жирного
заголовка читатель увидел `<b>Почему Bot API хватает</b>`. Ошибки не было — Bot API
ответил `200 OK` и вернул `message_id`.

## Причина: `parse_mode`

У метода `sendMessage` есть параметр `parse_mode` — режим разбора текста. Значения:

| Значение | Что означает |
|---|---|
| не передан | текст отправляется как есть, любые теги видны читателю |
| `HTML` | разбирается подмножество HTML (список тегов ниже) |
| `MarkdownV2` | разбирается Markdown; спецсимволы нужно экранировать |

Главное свойство: **отсутствие `parse_mode` — не ошибка**. Telegram не пытается
угадать, что в тексте разметка, и не предупреждает, что её там нашли, но не
применили. Режим «просто текст» — это валидный режим.

```python
params["parse_mode"] = "HTML"   # всегда, когда текст уже HTML
```

Второй вывод: если вы собираете текст из шаблона, `parse_mode` должен ставиться
там же, где шаблон, а не «где-то в обёртке».

## Проверка: `entities`

Ответ `sendMessage` содержит поле `entities` — список того, что Telegram реально
разобрал:

```json
{
  "message_id": 6,
  "text": "жирный и курсив, inline-код",
  "entities": [
    {"type": "bold",   "offset": 0,  "length": 6},
    {"type": "italic", "offset": 10, "length": 6},
    {"type": "code",   "offset": 18, "length": 10}
  ]
}
```

Практическая проверка в одну строку:

```python
len(message["entities"])  # 9 — разметка понята; 0 — ушло как текст
```

Отдельно полезно: у `pre` есть поле `language` — язык блока кода, который вы задали
через `<code class="language-python">`.

### Подвох: `offset` и `length` считаются в UTF-16

Документация прямо говорит: смещения — в единицах UTF-16, а не в символах. Для
кириллицы разницы нет, для эмодзи — есть: символ вне BMP занимает две единицы.

```python
def utf16_len(text: str) -> int:
    return len(text.encode("utf-16-le")) // 2

utf16_len("жирный")   # 6
utf16_len("🟢")        # 2, хотя len("🟢") == 1
```

Если вы режете текст по `entities` (подсветка, вырезание разметки, перенос в
другой формат), режьте по этим смещениям, а не по индексам Python.

## Негативный тест: а включён ли режим вообще?

Факт «сообщение доставлено» ничего не доказывает. Проверять надо возможность:
отправить заведомо сломанную разметку и убедиться, что Telegram её отверг.

```
$ python check_parse_mode.py --chat @my_channel
...
PASS  сломанный тег отвергнут (400 Bad Request: can't parse entities:
      Can't find end tag corresponding to start tag "b")
```

Если сломанный тег **принят** — значит `parse_mode` не применяется, и весь ваш
HTML уходит читателю как текст. Это единственный надёжный индикатор.

## Поддерживаемые теги (`parse_mode=HTML`)

Проверено отправкой: `bold`, `italic`, `underline`, `strikethrough`, `code`,
`spoiler`, `text_link`, `pre` (+`language`), `blockquote`.

| Тег | Результат |
|---|---|
| `<b>`, `<strong>` | жирный |
| `<i>`, `<em>` | курсив |
| `<u>`, `<ins>` | подчёркнутый |
| `<s>`, `<strike>`, `<del>` | зачёркнутый |
| `<span class="tg-spoiler">`, `<tg-spoiler>` | спойлер |
| `<code>` | моноширинный внутри строки |
| `<pre>`, `<pre><code class="language-python">` | блок кода, язык подсвечивается |
| `<a href="...">` | ссылка |
| `<blockquote>`, `<blockquote expandable>` | цитата, в т.ч. раскрывающаяся |

Чего нет: **заголовков, списков, таблиц, горизонтальных линий**. Их приходится
имитировать (жирная строка вместо заголовка, `•` вместо списка, выровненный
моноширинный блок вместо таблицы) — именно поэтому конвертер markdown → Telegram
не бывает «в одну строку».

## Лимиты, которые кусают

| Что | Лимит |
|---|---|
| текст сообщения | 1–4096 символов после разбора разметки |
| подпись к медиа | 0–1024 символа |
| медиагруппа | 2–10 файлов |
| широковещание | ~30 сообщений/сек |

Важно: 4096 считается **после** разбора сущностей, то есть по видимому тексту, а не
по длине HTML. Ошибка «message is too long» приходит уже на отправке — считайте
длину сами и режьте по смысловым блокам, не разрывая блок кода.

## Готовый скрипт

`check_parse_mode.py` в этой папке делает всё вышеописанное: отправляет образец
разметки, печатает типы сущностей, проверяет негативным тестом и удаляет за собой.

```bash
TG_TOKEN=123456:AA... python check_parse_mode.py --chat @my_channel
```

Полезно повесить в CI или в свой «деплой бота»: если ломается `entities` — вы
меняли формат или версию API, а не текст поста.

## Что дальше: rich messages

В Bot API 10.0 появился метод `sendRichMessage` (и `sendRichMessageDraft` для
потоковой генерации). Вместо `parse_mode` он принимает объект `rich_message` с
полями `html` или `markdown` и поддерживает блоки, которых нет в обычном HTML:
заголовки, списки, таблицы, выноски, раскрывающиеся блоки, формулы, медиа. Это
отдельная история — и отдельный пост.
