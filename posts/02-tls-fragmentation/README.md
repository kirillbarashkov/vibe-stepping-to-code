# 02. Фрагментация TLS резала не то поле

> Пост в канале: <!-- channel-link -->

## Симптом

Приложение ходит в API через `HTTPS_PROXY`. Сайт открывается в браузере, `curl` к тому
же хосту отдаёт `200`, а запрос к API обрывается на handshake — приложение показывает
«waiting on provider» и умирает по таймауту. Один хост, один IP, один путь.

## Диагностика

```bash
curl -s -o /dev/null -w "%{http_code}\n" --tls-max 1.3 https://<host>/   # ~1 с, обрыв
curl -s -o /dev/null -w "%{http_code}\n" --tls-max 1.2 https://<host>/   # 200
```

Работает 1.2, рвётся 1.3 — значит фильтр смотрит на то, что есть только в TLS 1.3.
Кандидат номер один — пост-квантовый key share `X25519MLKEM768`, который свежие
OpenSSL/BoringSSL предлагают по умолчанию.

## Почему стоковый инструмент не помогал

Upstream (NoDPI, GPL-3.0) фрагментирует **только SNI**: расширение с именем хоста,
куски по 2 байта, размер зашит в код, флагов `--fragment-size` / `--fragment-offset`
в проекте нет.

Key share лежит **вне** SNI и уезжает одним большим куском. Фрагментация формально
происходит — и не даёт ничего, потому что режется не то поле.

## Что сделано

Фрагментируется весь TLS-рекорд Client Hello: первые `offset` байт остаются целыми,
остальное делится на куски по `size` байт, каждый уходит отдельной записью `16 03 04`.

```bash
--fragment-size 32 --fragment-offset 100 --no-disorder --no-blacklist
```

Почему `offset 100`: заголовки записи и handshake, client random и session id уходят
одним нормальным куском, а key share никогда не попадает в сегмент целиком.

## Замеры

| Конфигурация | Handshake | Полная сессия (стриминг) |
|---|---|---|
| без фрагментации | обрыв за ~1 с | — |
| только SNI (дефолт) | обрыв | — |
| весь рекорд, size 1, offset 0 | проходит | **зависает**, байты не идут |
| весь рекорд, size 10, offset 0 | проходит | зависает периодически |
| весь рекорд, size 32, offset 100 | проходит | работает, включая стриминг |

## Две ловушки

1. **`curl` — плохой тест.** При size 1–10 он отдавал `200`, а приложение на том же
   эндпоинте висело: handshake завершается, соединение стопорится на первом большом
   ответе. Проверять только настоящим клиентом.
2. **Слишком мелкие куски — сами по себе аномалия.** Ни один реальный TLS-стек не режет
   по 1–2 байта; часть middlebox'ов такое дропает. 32 байта сохраняют правдоподобную
   форму сегмента.

## Прочие правки, без которых не запускалось

- `sys.stdout.reconfigure(encoding="utf-8")` — иначе на cp866/cp1252 падает на баннере
  с `UnicodeEncodeError`;
- проверка `sys.stdout and sys.stdout.isatty()` — иначе `AttributeError` в windowed-сборке;
- `MessageBoxW` вместо `input()` — иначе `RuntimeError: lost sys.stdin`.

## Что это не описывает

Никаких «обходов запретов»: речь о диагностике обрыва и починке собственной линии,
к которой приложение имеет полное право ходить. Названия провайдеров, адреса и чужие
сервисы в разборе не участвуют.
