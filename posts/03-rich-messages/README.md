# 03. Rich messages: настоящие блоки вместо имитации

## Что было

`parse_mode=HTML` поддерживает жирный, курсив, подчёркнутый, зачёркнутый, спойлер,
`code`, `pre` (с языком), ссылки и цитаты. Заголовков, списков, таблиц и
горизонтальных линий в нём нет — их приходилось имитировать (жирная строка вместо
заголовка, `•` вместо списка, выровненный `<pre>` вместо таблицы).

## Что появилось

Bot API 10.0 добавил **rich messages**: метод `sendRichMessage` и объект
`rich_message` с полями `html` или `markdown`. В 10.1–10.3 добавились медиа,
блоки, кнопки и потоковая генерация (`sendRichMessageDraft`).

Формат вызова — текст **вложен** в `rich_message`:

```python
params = {
    "chat_id": chat_id,
    "rich_message": {"markdown": "# Заголовок\n\n- пункт\n- пункт"},
}
# либо
params["rich_message"] = {"html": "<h1>Заголовок</h1><ul><li>пункт</li></ul>"}
```

## Грабля на входе

Плоское поле не работает:

```
sendRichMessage {"chat_id": ..., "html": "<h1>x</h1>"}
→ 400 Bad Request: rich message must be non-empty
```

Сообщение «пустое» вместо «неизвестный параметр» — легко решить, что метод не
поддерживается, хотя дело в форме запроса.

## Проверено на живом боте

| Запрос | Результат |
|---|---|
| `{"rich_message": {"html": "…"}}` | `ok`, в ответе есть поле `rich_message` |
| `{"rich_message": {"markdown": "…"}}` | `ok`, в ответе есть поле `rich_message` |
| `{"html": "…"}` (плоско) | `400 rich message must be non-empty` |

## Блоки, которые заявлены в API

`SectionHeading`, `Paragraph`, `List` + `ListItem`, `Table`, `BlockQuotation`,
`PullQuotation`, `ExpandableBlockQuotation`, `Details`, `Divider`, `Footer`,
`Preformatted`, `MathematicalExpression`, `Anchor`, `Buttons`, `Photo`, `Video`,
`Audio`, `VoiceNote`, `Document`, `Animation`, `Collage`, `Slideshow`, `Map`,
`Thinking`.

Для канала из этого важны четыре: заголовки, списки, таблицы и раскрывающиеся блоки —
именно их нельзя было сделать в `parse_mode=HTML`.

## Что надо проверить до переключения конвейера

1. **Рендер в клиентах.** API принимает — не значит «читается хорошо». Смотреть
   в мобильном приложении и в веб-версии, особенно таблицы на узком экране.
2. **Лимиты.** У rich messages свои ограничения на размер; считать их по правилам
   обычного текста (4096 после разбора) нельзя.
3. **Правка.** `editMessageText` для rich-сообщения требует параметр `rich_message`;
   обычная правка «уплощает» пост.
4. **Совместимость с пайплайном.** Конвертер markdown → HTML нужен только из-за
   ограничений классического режима; для rich messages markdown уходит как есть.
